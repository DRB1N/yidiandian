# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

This is a **Claude Code skill** called "yidiandian" (亿點點) — a practical, hands-on learning coach. It is not a traditional software project. The skill definition lives in `yidiandian/SKILL.md`; everything else in this directory supports it.

## Project Structure

- `yidiandian/SKILL.md` — The authoritative skill definition: persona, workflow, output format, and trigger keywords. Read this first before editing anything.
- `yidiandian/references/` — Reference documents used by the skill at runtime:
  - `rating_system.md` — D~S++ goal-distance rating system
  - `resource_evaluation.md` — 6-criteria resource quality rubric
  - `learning_theory.md` — Shortest-path learning methodology
- `yidiandian/scripts/` — Python helper scripts:
  - `calendar_generator.py` — Generates practice calendars (Markdown or .ics). Pure stdlib, run with managed Python.
  - `export_pdf.py` — Exports a learning plan as PDF (3-tier fallback: weasyprint → xhtml2pdf → HTML). Requires `jinja2`; run with venv Python.
- `yidiandian/assets/` — Templates:
  - `pdf_template.html` — Jinja2 template for PDF reports
  - `checklist_template.md` — Daily practice checklist template
- `多学亿点助手-工作流.yml` — Visual workflow definition for the SparkBot (讯飞开放平台) runtime. This is the no-code deployment artifact that runs the same logic as the skill inside a hosted chatbot. Edits to the skill logic should be reflected here too.
- `多学亿点助手.pdf` — Product documentation / design spec for the hosted app (42 MB, image-based — no extractable text).
- **The bot's opening greeting (开场白) is NOT in this repo.** It is the platform's `prologue` text field; the DSL export only carries `flowMeta.advancedConfig.prologue.inputExample` (the three clickable example chips, which ARE editable here). To change the greeting wording, edit it on the platform; only mirror the wording's rules into `yidiandian/SKILL.md`'s 开场白 section.

## Running the Scripts

```bash
# Calendar generator (pure stdlib, no venv needed)
python yidiandian/scripts/calendar_generator.py --plan '{"goal":"...","learning_path":[...]}' --output markdown

# PDF export (needs jinja2 in active env)
python yidiandian/scripts/export_pdf.py --plan '{"goal":"..."}' --output learning_plan.pdf
```

## Skill Runtime Rules (from SKILL.md)

1. **Mode first (J/P/ASK)**: decide whether the user wants serious planning (J), a quick usable result (P), or has given too little to tell (ASK) before anything else. **Both J and P are gated by the same completeness check**: J needs 成果 + 基础 + 时间/节点, and P needs BOTH a concrete practiceable object AND a settled 练法 — anything short of that is ASK, which asks up to 3 focused questions instead of answering. A vague goal like "我想学一首歌" is ASK, not P; so is "我想学《晴天》" (a bare song name does not say whether to sing it or play it, or on which instrument). Misjudging the mode is worse than misjudging the content.
2. **Always use WebSearch** for resource discovery — never rely on internal knowledge alone.
3. **Minimal Actionable Unit (MAU)**: every skill unit must be independently practiceable, startable within 15-30 minutes, not further decomposable, and independently verifiable. Filter candidates with "could they reach the goal without learning this?" — if yes, cut it.
4. **Shortest-path principle**: task/goal-oriented targets only include the minimum skills needed to reach the deliverable. Do not expand into full curriculum outlines.
5. **Video-first for hands-on skills** (music, dance, crafts, sports). Text supplements only.
6. **Never fabricate** resources, links, or evaluations. If search fails, degrade to generic resources for each skill unit.
7. **Gamified levels + objective self-assessment**: J-mode output is a level-based route where each level carries a goal-visible action, resource, quantitative pass criteria, and an externally observable self-check question. Never accept "掌握/熟悉/了解" as a pass criterion.
8. **Memory**: plans are written to `.workbuddy/memory/YYYY-MM-DD.md` (including current level and progress); user preferences go to `.workbuddy/memory/MEMORY.md`.

## Modifying the Workflow

The `多学亿点助手-工作流.yml` file is a SparkBot DSL v1 document. Its nodes mirror the skill's workflow steps:

```
开始 → 长期记忆检索_1 → 用户需求解析 ────────────────→ JP分类 (分支器)
   │                                        ├─ input1 == "J_READY" ─→ 历史学习检索
   │                                        └─ default ─────────────→ 信息是否完整
   │                                                                      ├─ input1 == "P_READY" → 即时方案生成 ┐
   │                                                                      └─ default (ASK) ────→ 保存待补目标 → 生成追问 → 结束
   历史学习检索 → 目标与技能拆解 → 搜索词生成 → 联网搜索_1/2/3 → 代码_1 → 资源初筛 → 资源筛选 → 资源覆盖核验 → 缺口补搜判定
                                                                    ├─ (== "NONE") → 资源归一化
                                                                    └─ default ────→ 二次补充检索 → 资源归一化
   资源归一化 → 学习路径生成 ─────────────────────────────────────────────────────────────────────────────┴→ 产出稿汇编
   产出稿汇编 → 事实质检 → 学习状态摘要 → 长期记忆写入_1 → 结束
```

The two branch nodes form a **three-way split**, because a `分支器` only has `input`/`input1` slots so each node can express exactly one `eq` test plus a default. `JP分类` peels off `J_READY`; `信息是否完整` peels off `P_READY`; **everything else (`ASK`) falls through to 追问**. That ordering is deliberate: an unrecognised or malformed value degrades to the 追问 path, which is the safe failure mode.

Key design points to preserve when editing:

- **Never hand-edit an existing node's `inputs`/`outputs` schema or its node ID.** The platform keeps a per-node protocol record; adding or removing declared fields makes the engine reject the node with `Node set output content ... does not match format`, and re-issuing the ID does NOT clear it. Add new behaviour as NEW nodes instead, cloned from a node whose schema is already proven. **Exception — the platform rewrites `outputs` itself and that is fine to leave alone:** switching a node to a non-thinking model (`isThink: false`) collapses its declared outputs from `[REASONING_CONTENT, output]` to a single `output` and drops `customParameterType: deepseekr1`. Both `生成追问` and `资源归一化` show exactly this in V5.0 after being moved to `Qwen3-Next-80B-A3B-Instruct`. So the prohibition is on *hand*-edits that desync the YAML from the protocol record, not on platform-driven output changes that accompany a model swap; do not try to restore `REASONING_CONTENT` by hand, and expect it to reappear on its own if a node is moved back to a thinking model.
- **Only these node shapes are known-good**: a `respFormat: 2` LLM node with declared outputs (`用户需求解析`, `搜索词生成`), a `respFormat: 0` LLM node (outputs `[REASONING_CONTENT, output]`, the model's whole reply becomes `output`), a `分支器`, and an `MCP` node. Clone those; do not hand-roll a new structured-output node.
- **A branch can only compare a scalar to a literal with `eq`.** Crucially, **compare against a value extracted by a `respFormat: 2` node, not against a `respFormat: 0` node's raw text.** The model's raw reply routinely carries a trailing newline or Markdown (e.g. `"J\n"`), which silently fails `eq "J"` and drops every request to the default branch. This is exactly the bug that made every question land on `即时方案生成`.
- **Because `用户需求解析` must keep its exact 12-field schema, the J/P/ASK decision is carried by overloading its `need_clarification` field** (prompt-only change). It emits exactly one of `J_READY` / `P_READY` / `ASK`, never `true` / `false`:
  - `J_READY` = J 型且 goal + current_level + (weekly_time 或 deadline) 齐全；
  - `P_READY` = P 型且目标是具体可练的对象（泛指的量词短语如"我想学一首歌"／"我想学编程"一律不算，必须落 `ASK`）**且练法已明确**；一首歌只给歌名、没说唱还是弹（弹哪种乐器），同样必须落 `ASK`；
  - `ASK` = 其余全部，包括 J 缺信息、目标太泛、练法未定、上一轮追问没答完、判不出 J/P。
  `JP分类` matches `J_READY`, `信息是否完整` matches `P_READY`, and `ASK` falls through to 追问. If you alter that vocabulary you must change both branch literals and the prompts of `用户需求解析`, `生成追问`, `即时方案生成`, `产出稿汇编` and `事实质检` together.
  **`用户需求解析` now opens with a self-contained 「三问定档」 decision card + 整句范例, and closes with a 打钩 checklist** — the long rules in between are kept, but the card is what the model actually follows. This is the fix for "我想学首歌" landing on `P_READY`: the old prompt hammered 「判为 P」 in its priority list (二-2 / 二-5) while the completeness gates sat far away in 六-B, so a weak model read "模式 = P" as "may answer". Every such line now ends with "这只是把「模式」判为 P，不代表信息已经够了". Keep that pattern if you rewrite it: **the mode judgement and the completeness judgement must never be expressible as the same word.**
- **The clarification loop needs multi-turn context, so three nodes carry `enableChatHistoryV2 = {isEnabled: True, rounds: 3}`**: `用户需求解析`, `生成追问`, `即时方案生成`. Without it the graph is amnesiac between turns — a bare "晴天" answering three earlier questions looks like a brand-new P request, the model has no record of what it already asked, and it answers instead of re-asking. This is a value-only change to an existing `nodeParam` key (the key is present on every node with the value `{isEnabled: False, rounds: 1}`, so flipping it adds/removes nothing). NOTE: the ONLY precedent for a value-level `nodeParam` change breaking the platform is blanking `uid`, which produced `Protocol update failed` — if the canvas ever rejects this flip, revert those three keys to `{isEnabled: False, rounds: 1}` and rely on the prompts alone.
- **`missing_fields_text` is the routing-relevant token list, so encode "练法" into it** rather than adding a schema field. For any skill where one object has several ways to practise it (a song can be sung / played on guitar / played on piano; a sport can be singles or doubles), if the user has not said which, `用户需求解析` must list `练习方式` among the missing items. `生成追问` then asks it first, with options, and `即时方案生成` refuses to answer when it is unsettled.
- **One question, one thing.** `生成追问` must never bundle two asks into a sentence — the concrete counter-example to keep in the prompt is `"你现在对唱歌或乐器的基础如何？比如是完全新手，还是能弹点吉他？"`, which conflates "sing or play, and which instrument" with "what level", so the user answers only one and the other is silently dropped forever.
- **`即时方案生成` must never invent an unsettled premise.** Its inputs are only mode/goal/domain/level, so when the 练法 is unknown it used to guess — 《晴天》 came back as a guitar lesson. Its prompt now self-checks for this and emits a single clarifying question with no 任务难度 instead of a plan. Do not "fix" this by adding inputs; the gate belongs upstream in `用户需求解析` → `ASK`.
- **`信息是否完整` is an original node** (label kept, its name now reads correctly as "信息够不够直接作答"): its input ref still points at `need_clarification`; only its `input1` literal changed (`"true"` → `"P_READY"`) and its two case targets were swapped. Reuse it rather than adding a third branch node.
- **`缺口补搜判定` compares a `respFormat: 0` reply to `"NONE"`**, which is inherently lossy. It is safe because a miss degrades gracefully (one extra search whose junk is dropped by `资源归一化`). Do not rely on it for anything that must not misfire.
- **The platform has no arbitrary back-edges** — the multi-round search is unrolled into one explicit second wave gated by `缺口补搜判定` (max 2 rounds). Do not wire a cycle into the graph.
- **`产出稿汇编` merges the J and P drafts** so that `事实质检` keeps a single `draft` source. It maps `need_clarification` → the marker `【模式：X】` (X ∈ J/P/ASK), which is how `事实质检` and `学习状态摘要` learn the mode without an extra input slot. **The marker is form-checked rather than blind-copied**: a draft that is nothing but a clarifying question (no 目标评级, no 闯关, no 任务难度) is marked `【模式：ASK】` even when `need_clarification` said `P_READY`. That is the graph's second line of defence against a vague goal leaking down the P path.
- **`资源归一化` is the single source of `resources`** for `学习路径生成`, so both search waves converge before the downstream node.
- **Leave the `uid` on the `长期记忆检索` / `长期记忆写入` nodes exactly as the platform stamped it.** `uid` appears on most nodes (LLMs, branches, MCP) as the *account* identity, and the memory nodes reuse the same field. It is tempting to blank it to force an executor fallback, but the platform rejects that with `Protocol update failed` at test time. The four memory nodes' `nodeParam` is byte-identical to the pristine original and must stay that way.
- **Per-user memory isolation is the platform's job, not the graph's — do not try to build it here.** Confirmed by testing: switching accounts on the published bot yields separate memory, so the runtime already partitions by the real end user; the stamped `uid` is only the designer's identity. The corollary matters when demoing: the **canvas debug panel runs every visitor as one identity**, so it shows shared memory there. A fresh conversation recalling earlier memories is *not* a bug either — long-term memory is cross-session by design. Verify isolation on the published bot with two accounts, never in the canvas.
- **Never put a date/time field into a memory write.** `学习状态摘要` used to emit a hard-coded `updated_at`, which made every record look like it was written on that same day; the memory store already timestamps entries (`长期记忆检索.memory` exposes a `date` per entry). There is no clock available in-graph, so omit timestamps rather than guess one.
- **`事实质检` must never emit an empty section heading.** If a J-structure section has no content, delete the heading; only `目标评级` may be synthesized, and only when goal and level are known. The empty `目标评级` the user saw was `事实质检` padding a P draft it had been told was a J draft.
- **`事实质检` runs the last two gates in the graph, and they are the only ones that see the finished text.** (a) **Link gate** — a cited link must both exist in `可信资源` *and* match the level it is attached to, and the match is judged on the resource **title** (it must name that level's core object; "same broad field / same platform / same泛主题" is a miss). On a miss the link is deleted outright — never swapped for another — and the level's resource slot becomes `暂未检索到可信资源` plus a suggested search keyword. This is the fix for the "最后给出的链接很大概率是无关链接" complaint: previously rule 1 only checked *presence in the list*, so an irrelevant-but-real URL sailed through. (b) **P-mode gate** — a P draft whose 任务难度 line is followed by no actionable content (no 动作/谱/参数/代码/步骤) is reclassified ASK: strip the marker line, the 任务难度 line and the P closing line, keep only the question. Gate (b) is the backstop for the router leaking "我想学首歌" into the P path.
- **The J route and the P route must not share closing lines.** `学习路径生成` (J) ends with `如果情况有变化，请及时告知我，我来帮你优化路线。`; `即时方案生成` (P) ends with `想要带资源链接、验收标准和进度的完整版，说一声。` `事实质检` must delete the P line if it appears in a J draft — the two were leaking into each other after the model swap, so both rules are now stated explicitly rather than by omission.
- **Every LLM node in the graph runs on `Qwen3-30B-A3B`** (`modelId`/`llmId` 223, `serviceId`/`domain` `xop3qwen30b`) — the user swapped them all off DeepSeek-R1 for speed. This is a ~3B-active model and follows instructions far more loosely than the DeepSeek-R1 it replaced. Practical consequences when editing prompts: (a) state branch-specific rules explicitly as *both* the do and the don't — never rely on "this rule only applies to the other mode" as an implicit exclusion, because the model bleeds it across branches; (b) keep each rule's *decision* near the top of the prompt and repeat the critical ones at the very end, because a long prompt buries mid-document rules.
- **`maxTokens` is 4096 on the five output-heavy nodes** (`学习路径生成`, `产出稿汇编`, `事实质检`, `资源初筛`, `资源归一化`) and 2048 on the rest. 2048 truncated the J route mid-URL (3455 chars in, ending inside a link), which is why those five were raised. If a node's output starts getting cut, raise this field rather than shortening the prompt.
- **Do NOT trust a single `respFormat: 2` failure as proof that a model is incompatible — the 2026-09-12 one did not reproduce.** In that episode the canvas rejected `用户需求解析` and `搜索词生成` with `Node set output content {'query_3': '', 'REASONING_CONTENT': '', 'query_1': '', 'query_2': ''} does not match format` right after they were pointed at `Qwen3-235B-A22B-Instruct-2507` / `Qwen3-Next-80B-A3B-Instruct`; the same big-model tiering then ran fine later, with no diagnosed change in between. So this error means only **"the node got no usable structured reply"** — every declared output came back empty. At least three unrelated causes produce that, and the message cannot tell them apart: (a) genuine model/structured-output incompatibility; (b) a transient upstream failure — model not yet activated on the account, cold start, rate limit, timeout — returning an empty reply; (c) a stale per-node protocol record the platform refreshes on a later save or run. Because all four fields are empty *including* `REASONING_CONTENT`, (b) and (c) are at least as likely as (a): a model that answered in the wrong shape usually leaves something partially parseable, whereas nothing at all looks like no reply. Before acting on this error: **re-run it twice, and re-export the DSL to see what the canvas actually holds.** Note `respFormat: 0` does no such validation (the whole reply becomes `output`), so those nodes can only get worse content, never hard-fail. One real asymmetry worth knowing: `REASONING_CONTENT` (`customParameterType: deepseekr1`, and no `required: false`, so required by default) is emitted only by **thinking-mode** models — `Qwen3-30B-A3B` and `Qwen3-235B-A22B` are thinking models, `…-Instruct-2507` / `…-Instruct` are the non-thinking variants — and `query_1` is likewise the only query field without `required: false`. That plausibly matters, but it is declared on **all 13** LLM nodes and must never be edited: removing a declared output field is what permanently wedges a node.
- **The intended end state is a model tiering across all 13 LLM nodes, applied by hand in the canvas — this is what the published `多学亿点助手V5.0.yml` carries, and it has been observed running.** Real stamps, read off that platform export on 2026-09-12 rather than guessed: `Qwen3-30B-A3B` = 223 / `xop3qwen30b`; `Qwen3-235B-A22B-Instruct-2507` = 225 / `xop3qwen235b2507`; `Qwen3-Next-80B-A3B-Instruct` = 10000021 / `xop3qwen80bnext`; `DeepSeek-R1` = 142 / `xdeepseekr1` (per the 优化前备份). All share `url` `wss://maas-api.cn-huabei-1.xf-yun.com/v1.1/chat`, `patchId` `'0'`, `model` `spark`. **Never write a model ID into the YAML** — models are chosen in the canvas, and a guessed `serviceId`/`domain` makes the platform reject the whole import; `多学亿点助手-工作流.yml` therefore stays on `Qwen3-30B-A3B` everywhere. The tiering, applied by hand: `Qwen3-235B-A22B-Instruct-2507` on the 7 nodes that must reason or discriminate (`用户需求解析`, `搜索词生成`, `目标与技能拆解`, `资源筛选`, `学习路径生成`, `事实质检`, `即时方案生成`), `Qwen3-Next-80B-A3B-Instruct` on the middle tier (`生成追问`, `资源归一化`), and `Qwen3-30B-A3B` on the 4 mechanical nodes (`资源初筛`, `资源覆盖核验`, `产出稿汇编`, `学习状态摘要`). That split — including both `respFormat: 2` nodes on 235B — is what `多学亿点助手V5.0.yml` carries, and it runs. **Swap ONE node at a time and re-run a full J request before doing the rest**: batching the swaps is what made the one transient failure above so hard to attribute.
- **`代码_1`** is an `ifly-code` node holding hand-written Python: `main(content_1, content_2, content_3)`, fed by the three `联网搜索` nodes' `result.content` arrays (declared `array-object`, though the code does `str()` on them). It collapses whitespace, truncates each source to 2500 chars with a trailing `……`, drops empties, and prefixes each with `【搜索器N】`. **`N` is pinned to the query index (`query_1/2/3`), not to the position after filtering** — an empty wave leaves a gap rather than relabelling 搜索器2 as 搜索器1, so 资源初筛 can always tell which query a block came from. Its output `compressed_results` is the whole concatenated blob.
- **An `ifly-code` node's `code` field must be raw Python — no Markdown fence, no `import`, no f-string, and a `# -*- coding: utf-8 -*-` first line if it contains Chinese.** The stored `code` originally began with a literal ```` ```python ```` and ended with ```` ``` ````, which is a `SyntaxError` at parse time and surfaces only as the generic `Code execution failed`. Rewriting it as defensive Py2/Py3-compatible source (plain `.split()`/`" ".join()` instead of `re`, `%`/concatenation instead of f-strings) removed three separate plausible causes at once. `compressed_results` is a `string` output, so keep `main` returning a `str`.
- **`资源初筛` is a NEW `respFormat: 0` LLM node inserted between `代码_1` and `资源筛选`** (cloned from `资源筛选`, fresh uuid on the node and all four slot ids). Inputs: `result` ← `代码_1.compressed_results`, `goal` ← `用户需求解析.goal`. It does de-noise only — drop entries with no real URL/source, dedupe by URL, drop ads/nav pages, merge near-duplicates, compress each survivor to one line (`标题 | URL | 平台 | 一句话要点`), cap at 15. It must not *score* relevance and must not invent anything — relevance scoring stays in `资源筛选` — but it does drop entries whose **title** shows they are off-topic, plus platform homepage / category / search-result / aggregator / download-site / netdisk / forum-Q&A / 贴吧 / 百科 pages. Judging topic from the title only (never from a keyword mentioned somewhere in the summary) is what keeps this cheap enough for a weak model. Splitting the work this way is what keeps `资源筛选`'s input small.
- **`资源筛选` keeps 1 resource per skill unit, max 5 total** (was 1–2 / max 8). If you change that cap, change it in the prompt only — there is no schema field for it. **Its step 0 is a topicality gate and it is the whole point of the node**: match on the resource **title** — it must name that unit's core object (song title, proper noun, tool/API name). "Same broad field" is a reject: unit `《晴天》吉他弹唱` vs resource `吉他入门全套教程` fails, as does `Python 列表推导式` vs `Python 从入门到精通`. Resources scoring below 70 on relevance are never selected, and an uncovered unit goes into `missing_resource_skill_ids` rather than receiving a weak filler. `资源归一化` then re-applies the same title test to the second search wave and caps the final list at 6 (down from 10).
- **A tool-node insertion must be done as `retarget the existing edge + append one new edge`**, changing the existing edge's `id` to match the new pair (`reactflow__edge-<src>-<tgt>`, no handle part when there is no `sourceHandle`). Do not delete and re-add edges by hand — the `id` encodes the endpoints.

When changing system prompts or adding steps, update both the skill definition and the corresponding node's `systemTemplate` / `template` fields in the YAML.

Two snapshots are kept beside the live file (the repo is not under version control): `多学亿点助手-工作流.优化前备份.yml` (the generated bot's output before the first optimization pass) and `多学亿点助手-工作流.修正前备份.yml` (the state before the routing/link fixes described above). Back up to a new `.修正前备份.yml`-style name rather than editing over a snapshot.

The DSL rewrite is safe to do with PyYAML round-trip (`safe_load` → patch → `dump(sort_keys=False, allow_unicode=True, default_flow_style=False, width=100000)`) as long as you then deep-compare old vs new and assert that the *only* differing paths are the ones you meant to touch — see `_tmp/patch.py` and `_tmp/deepdiff.py`. The platform tolerates the reformatting (block vs flow style, `'0'` vs `0`), but it will not tolerate a lost node field, a changed edge `id`, or a dropped `uid`.
